# HIN Parser & PostgreSQL Migrator

Автор: SilvSane

Консольная утилита на Node.js, которая парсит научные файлы структуры фуллеренов (.hin) и переносит данные в базу PostgreSQL. Утилита ведёт пользователя через интерактивные вопросы, а при отсутствии базы умеет создавать её автоматически.

## Требования

- Node.js 20.6 или новее. Утилита использует нативный флаг `--env-file` и top-level await.
- PostgreSQL 14 или новее, установленный локально или запущенный в Docker.

Для запуска через Docker понадобится Docker Desktop или Docker Engine с плагином Compose.

## Возможности

- Идемпотентность: повторный запуск с тем же именем таблицы удаляет старую таблицу и создаёт новую, дублей не появляется.
- Последовательное выполнение: используются ES-модули и top-level await, чтобы файловые и сетевые операции шли строго по порядку.
- Параметризованные SQL-запросы: все вставки идут через плейсхолдеры, пользовательские данные не могут сломать запрос.
- Единый конфиг через .env: креды, подключение и папка с .hin файлами читаются из одного файла окружения.
- Автосоздание базы: если базы из .env нет на сервере, утилита подключается к системной базе `postgres` теми же кредами и выполняет `CREATE DATABASE`.
- Понятные ошибки подключения: при сбое печатается код ошибки драйвера, короткая подсказка, содержимое .env.example и SQL для ручного исправления.
- Интерактивный ввод: спрашивает путь к .hin и имя таблицы, проверяет оба, при ошибке переспрашивает, не завершаясь.
- Терпимый парсер: поддерживает разные варианты .hin (C30 с маркером `**`, C70 с `CA`, другие с произвольным маркером вроде `CR`). Данные атома находятся по первому числовому токену после маркера, поэтому парсер не привязан к конкретной строке маркера.

## Настройка окружения

Скопируйте `.env.example` в `.env` и заполните значения. Кавычки не использовать.

```
DB_USER=postgres
DB_HOST=localhost
DB_DATABASE=postgres
DB_PASSWORD=ваш_пароль
DB_PORT=5432
HIN_DIR=N:/Computer Moduling Physics/fullerens
```

Замечания по .env:

- Значения нельзя оборачивать в кавычки. Docker Compose считает кавычки частью значения, поэтому `DB_PASSWORD="secret"` превратится в пароль `"secret"` с литеральными символами кавычек.
- Исключение — значения с пробелами или спецсимволами. Если кавычки всё же нужны, используйте одинарные: они подавляют подстановку переменных в Compose. Двойные не спасают от `$`.
- `HIN_DIR` используется только в режиме Docker. Указывает на папку на хосте, которая будет смонтирована в контейнер. Локальный режим эту переменную игнорирует.
- `DB_HOST=localhost` подходит для локального запуска. В Docker `DB_HOST` автоматически переопределяется на `db` из docker-compose.yml.
- `.env` находится в .gitignore. Никогда не коммитьте его.

## Локальный запуск

Этот путь подходит, если PostgreSQL установлен на той же машине или доступен по сети, и вы хотите запускать утилиту напрямую через Node.

1. Установите зависимости.

   ```
   npm install
   ```

2. Убедитесь, что PostgreSQL запущен и доступен с кредами из .env. Если базы с именем из `DB_DATABASE` ещё нет, создайте её вручную через psql или pgAdmin, либо позвольте утилите создать её при первом запуске.

3. Запустите утилиту.

   ```
   npm start
   ```

Сначала утилита проверяет подключение к базе. Если базы нет, но сервер доступен, она создаёт базу и продолжает. Если сервер недоступен или креды неверные, печатает диагностику и завершается.

После проверки утилита спрашивает путь к .hin файлу. Можно вставлять путь в формате Windows или Unix, с прямыми или обратными слэшами, в кавычках или без. Утилита нормализует ввод, проверяет, что файл существует, и что расширение .hin. После принятия файла печатается его размер, затем запрашивается имя таблицы.

## Запуск через Docker

Этот путь подходит, если хочется изолированное окружение с управляемым PostgreSQL и без локальной установки.

1. Убедитесь, что `HIN_DIR` в .env указывает на папку с .hin файлами на хосте. Папка должна существовать до первого запуска, иначе Docker создаст пустую директорию от имени root.

2. Соберите образ приложения.

   ```
   docker compose build
   ```

3. Запустите контейнер с базой в фоне.

   ```
   docker compose up -d db
   ```

4. Дождитесь, пока база перейдёт в состояние healthy.

   ```
   docker compose ps
   ```

   В колонке STATUS должно быть `Up (healthy)`. Обычно это занимает несколько секунд после первого запуска.

5. Запустите утилиту в интерактивном режиме.

   ```
   docker compose run --rm app
   ```

   Так запускается временный контейнер с привязанным терминалом, и интерактивные вопросы работают корректно. Флаг `--rm` удаляет контейнер после завершения, что и нужно для одноразовой утилиты.

6. Когда утилита спросит путь к .hin файлу, используйте путь со стороны контейнера. Всё, что лежит в `HIN_DIR` на хосте, доступно как `/hin` внутри контейнера. Например, если файл на хосте — `N:/Computer Moduling Physics/fullerens/c38.hin`, введите `/hin/c38.hin`.

   Чтобы убедиться, что видно внутри контейнера, выполните:

   ```
   docker compose run --rm app ls /hin
   ```

7. Чтобы остановить базу и удалить контейнеры, сохранив данные:

   ```
   docker compose down
   ```

   Чтобы удалить и volume с данными:

   ```
   docker compose down -v
   ```

## Интерактивные вопросы

Утилита начинает с короткого баннера и напоминания про Ctrl+C, который прерывает процесс в любой момент.

Первый вопрос: путь к .hin файлу. Ввод нормализуется, затем проверяется. Проверка отсеивает пустой ввод, несуществующие файлы, директории и файлы с расширением, отличным от .hin. Ошибка печатается сразу, вопрос повторяется.

Второй вопрос: имя таблицы PostgreSQL. Правила валидации:

- Непустая строка.
- Длина не больше 63 символов.
- Разрешены латинские буквы, цифры и знак подчёркивания. Первым символом не может быть цифра.
- Имя не должно совпадать с зарезервированным словом SQL, таким как `select`, `insert`, `drop`, `user`, `table`.

Если имя прошло валидацию, но вставка упала на уровне базы, утилита печатает ошибку и снова запрашивает имя таблицы, не завершаясь. Ctrl+C прерывает процесс.

## Поведение при ошибках подключения

Перед тем как что-либо спросить, утилита вызывает `ensureDatabase`. Логика такая:

1. Пробуем подключиться к целевой базе с кредами из .env. Если подключение удалось, продолжаем.
2. Если драйвер вернул `3D000` (база не существует), подключаемся к системной базе `postgres` теми же кредами, проверяем `pg_database` на целевое имя, и при отсутствии выполняем `CREATE DATABASE`. Затем переподключаемся к целевой базе и продолжаем.
3. Если возникла любая другая ошибка, печатаем диагностику и завершаемся с кодом 1.

Диагностический блок содержит код ошибки, короткую подсказку, содержимое .env.example и SQL для ручного запуска, если автоматическое создание невозможно.

Частые коды ошибок:

- `ECONNREFUSED`: сервер не запущен, либо неверный хост или порт.
- `ENOTFOUND`: имя хоста не разрешается.
- `ETIMEDOUT`: превышено время ожидания подключения.
- `28P01`: неверный пароль пользователя.
- `28000`: неверная спецификация авторизации.
- `3D000`: база данных не существует.
- `42501`: недостаточно прав для создания базы.

Если подключение отклонено или истекло время ожидания, утилита завершается. Если базы нет, но креды рабочие, база создаётся автоматически.

## Структура базы данных

Для каждого обработанного файла создаётся таблица со следующими колонками:

- `id` (SERIAL PRIMARY KEY)
- `atom_number` (INTEGER)
- `energy` (NUMERIC)
- `x`, `y`, `z` (NUMERIC), пространственные координаты атома
- `connection_count` (INTEGER)
- `connections` (INTEGER[]), массив индексов связанных атомов
- `connection_types` (TEXT[]), массив символов типов связей

Повторный запуск с уже существующим именем таблицы сначала удаляет старую таблицу, поэтому таблица всегда отражает последний импорт.

## Поддерживаемые форматы .hin

Парсер читает блок `mol`, пропускает строки `vel` и прочие метаданные, и обрабатывает только строки, начинающиеся с `atom`. В каждой строке атома он идёт по токенам и начинает читать числовые данные с первого токена, похожего на число. Благодаря этому парсер не зависит от конкретного маркера, который может быть `**`, `CA`, `CR` или любым другим в зависимости от источника.

Если парсер встречает нечисловой токен там, где ожидалось число, он бросает ошибку с номером строки и её содержимым, поэтому проблему видно сразу, без похода в логи базы.

## Диагностика типичных проблем

`docker compose` пишет `services.volumes must be a mapping`. Это проблема отступов в YAML. Каждый уровень — ровно два пробела. Блок `volumes:` верхнего уровня должен стоять в нулевой колонке, вне сервисов.

`docker compose run app` не принимает ввод с клавиатуры. В сервисе app должны быть одновременно `stdin_open: true` и `tty: true`. Без них интерактивный промпт не отрисуется.

PostgreSQL при первом запуске в Docker сообщает `invalid password for user` (код 28P01). Пароль, зашитый в volume базы, не совпадает с тем, что в .env. Переменные вида `POSTGRES_PASSWORD` действуют только при первичной инициализации volume. Чтобы переинициализировать, выполните `docker compose down -v` и запустите заново.

Утилита пишет `not found: /app/N:\...\file.hin`. Путь введён в формате Windows, а утилита работает внутри Linux-контейнера. Используйте путь со стороны контейнера, например `/hin/file.hin`.

PostgreSQL пишет `invalid input syntax for type integer: "NaN"`. Парсер не смог найти числовое поле в строке атома. Текущий парсер смягчает это тем, что ищет первый числовой токен и валидирует каждое разобранное значение, поэтому сообщение укажет на конкретную строку.

Приложение не подключается к базе из Docker. Проверьте, что `DB_HOST` в сервисе app равен `db`. Внутри контейнера `localhost` указывает на сам контейнер, а не на хост или сервис базы.

Порт 5432 уже занят. Возможно, локально запущен PostgreSQL. Остановите его или поменяйте проброс порта в docker-compose.yml на `"5433:5432"`, оставив внутренний `DB_PORT: 5432` без изменений.

Интерактивный промпт показывает устаревший список файлов или дерево. Это была проблема более ранней версии утилиты. Текущая версия использует обычное текстовое поле для пути и не рисует дерево.

## Разработка

Проект использует ES-модули. В `package.json` указано `"type": "module"`, поэтому все .js файлы используют `import` и `export`.

Каталог `src` сгруппирован по ответственности:

- `src/cli` содержит интерактивный слой.
- `src/config` содержит настройки, производные от окружения.
- `src/db` содержит доступ к базе, проверку подключения и создание схемы.
- `src/parsers` содержит чтение .hin.

Точка входа — `src/main.js`. Она проверяет подключение, затем крутит интерактивные вопросы, пока не получит валидное имя таблицы и успешную вставку.
